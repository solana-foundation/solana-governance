# Delegate Vote

Let another key create, support and vote on proposals for your validator, so the validator identity key never has to sign governance transactions.

## Description

By default the governance voter for a vote account is its **node identity**, the hot key that runs the validator. Signing governance transactions with it is tedious and poor key hygiene. A **vote delegation** names a different key, the **delegate**, as the governance voter for the vote account.

Delegation is a two-step handshake, so a mistyped key can never lock you out:

1. `delegate-vote`, signed by the vote account's node identity **or** authorized withdrawer, names the delegate. The delegation is **pending** and has no effect yet: the identity keeps voting.
2. `accept-vote-delegation`, signed by the delegate, activates it. From then on the delegate alone may `create-proposal`, `support-proposal`, `cast-vote`, `modify-vote` and `update-proposal-description` for the vote account, and the identity key is **locked out** of governance until the delegation is removed.

All on-chain records stay attributed to the validator: a `Vote` cast by the delegate still names the identity, counts the validator's full stake, and can be overridden by stakers exactly as before.

<Callout type="info">
  The delegate can be any key that can sign a transaction, including a multisig vault PDA such as Squads (acceptance is signed through the multisig). Delegating to a Squads vault from this CLI is not yet supported; use the multisig's own tooling to sign the `accept_vote_delegation` instruction.
</Callout>

## Removing a delegation

`remove-vote-delegation` closes the delegation and returns its rent to whoever created it. Who may remove depends on whether it was accepted:

| Signer | Pending | Accepted |
|---|---|---|
| Delegate | Yes | Yes (resign) |
| Authorized withdrawer | Yes | Yes (revoke) |
| Node identity | Yes | **No** |

The authorized withdrawer is the cold root authority of the vote account, so a lost or hostile delegate key never strands the vote: the withdrawer revokes and the identity votes again (or delegates to a new key).

<Callout type="warning">
  Once accepted, the identity key cannot vote or revoke. Keep the authorized withdrawer key safe; it is the escape hatch.
</Callout>

## Usage

```bash
# 1. As the validator identity: name the delegate
svmgov -k /path/to/identity.json delegate-vote --delegate <DELEGATE_PUBKEY>

# 2. As the delegate: accept
svmgov -k /path/to/delegate.json accept-vote-delegation --vote-account <VOTE_ACCOUNT>

# 3. As the delegate: vote as usual. The CLI finds the delegated vote account.
svmgov -k /path/to/delegate.json cast-vote --proposal-id "ABC123..." \
  --for-votes 10000 --against-votes 0 --abstain-votes 0

# Inspect
svmgov show-vote-delegation --vote-account <VOTE_ACCOUNT>

# Remove (delegate, withdrawer, or identity while pending)
svmgov -k /path/to/delegate.json remove-vote-delegation
svmgov -k /path/to/withdrawer.json remove-vote-delegation --vote-account <VOTE_ACCOUNT>
```

## Commands

### `delegate-vote`

| Argument | Type | Required | Description |
|---|---|---|---|
| `--delegate` | String | **Yes** | Base58 pubkey that will vote for the vote account |
| `--vote-account` | String | No | SPL vote account to delegate. Defaults to the one whose node identity is the signer; required when signing as the authorized withdrawer |

### `accept-vote-delegation`

| Argument | Type | Required | Description |
|---|---|---|---|
| `--vote-account` | String | **Yes** | SPL vote account whose pending delegation to accept |

### `remove-vote-delegation`

| Argument | Type | Required | Description |
|---|---|---|---|
| `--vote-account` | String | No | SPL vote account whose delegation to remove. Defaults to the signer's own vote account, or the one delegated to the signer |

### `show-vote-delegation`

| Argument | Type | Required | Description |
|---|---|---|---|
| `--vote-account` | String | **Yes** | SPL vote account to inspect |
| `--json` | flag | No | Print the delegation as JSON |

## Acting as a delegate

Every validator command accepts `--vote-account`. Without it the CLI resolves the vote account from the signer: first the vote account whose node identity is the signer, then the single vote account with an accepted delegation naming the signer. A delegate for several validators must pass `--vote-account` to choose one.

## What Happens On-Chain

- `delegate_vote` reads `node_pubkey` and `authorized_withdrawer` from the live SPL vote account, requires the signer to be one of them, and creates a `VoteDelegation` PDA (seeds `["vote_delegation", vote_account]`) with `delegation_accepted = false`.
- `accept_vote_delegation` requires the delegate's signature and sets `delegation_accepted = true`.
- `create_proposal`, `support_proposal`, `cast_vote`, `modify_vote` and `update_proposal_description` take the `VoteDelegation` PDA as an account. With an accepted delegation the signer must be the delegate; otherwise the signer must be the identity (the snapshot's `voting_wallet` for votes).
- `remove_vote_delegation` closes the PDA to its creator under the rules in the table above.
